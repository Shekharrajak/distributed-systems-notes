One transaction across many Kafka brokers

Partition leaders own logs. Coordinators own keys mapped to internal-topic partitions. A transaction records one durable decision, then delivers that decision to every participant.

2. Where does each coordinator live?

A coordinator is a service inside a broker process, with ownership divided into shards. It is not one dedicated coordinator machine for the entire cluster. BrokerServer constructs the services; leadership of their internal-topic partitions determines which shards each broker actively serves.

4. What happens before commit?

  1. Acquire: ShareFetch goes to the source-serving leader. The application receives records acquired for its member. The group coordinator manages membership; it does not relay every data record.
  2. Produce: the worker sends transactional output to the current output leaders. Their logs retain producer ID/epoch and sequence metadata. Participant registration/verification follows the negotiated transaction protocol.
  3. Acknowledge locally: the worker records ACCEPT/REJECT and drains acknowledgements for the producer transaction. Local acknowledge is not yet a durable source completion.
  4. Stage: producer TxnShareAcknowledgeHandler targets the source topic partition. KafkaApis.handleTxnShareAcknowledgeRequest checks feature gates, authorization, batches and membership, maps source keys to share-state partitions, and calls AddPartitionsToTxnManager.addOrVerifyTransaction to register those partitions.
  5. Persist pending state: after registration, SharePartitionManager.acknowledgeTransactional calls SharePartition.stageTxnAcknowledge. Acquired records become TX_PENDING with staged producer ID, epoch, ACK type and intended disposition. The acquisition timer is cancelled. writeShareGroupState uses the persister to write to the appropriate share-state coordinator.
  6. Await success: the application must finish all output sends and acknowledgement staging before committing. A failure can leave partial work across partitions; transaction abort/recovery resolves it. Registration itself is not proof that an acknowledgement was staged.

ACCEPT and REJECT are the user acknowledgement choices allowed here; RELEASE and RENEW are not transactional. Internal gap acknowledgements also exist for offsets without an application record. Before durable staging, acquisition timeout governs redelivery; after staging, transaction completion governs it.

Source leaders can talk to remote share-state leaders through the persister. This remote persistence path exists independently of the missing remote membership-validation path.

6. What exactly changes in the output log?

MemoryRecords.withEndTransactionMarker builds a control batch. The broker calls ReplicaManager.appendRecords with coordinator origin and requiredAcks=-1. Acknowledgement follows the partition replication policy; this is not a claim that every configured replica or every disk has fsynced.

  1. ProducerAppendInfo.appendEndTxnMarker checks producer and coordinator epochs. If the producer has an open data transaction, it constructs a CompletedTxn with first offset, marker offset and abort flag; then updates producer state.
  2. UnifiedLog append processing computes the transaction's last stable offset, updates the transaction index, and calls ProducerStateManager.completeTxn.
  3. completeTxn removes the transaction from ongoingTxns and retains it in unreplicatedTxns until high-watermark progress makes completion stable.
  4. UnifiedLog.lastStableOffset limits committed reads by both the high watermark and earliest unstable transaction. An earlier open transaction can still hold back later committed output.
  5. The abort index identifies aborted ranges. The ordinary consumer's CompletedFetch skips aborted transactional batches for read_committed and never returns control records as user records.
Before: [X, transactional, producer=700] [Y, transactional, producer=700]
After:  [X, transactional, producer=700] [Y, transactional, producer=700] [COMMIT]

No payload rewrite. ABORT adds an abort marker; it does not delete X and Y.

read_uncommitted readers can observe data before the transaction resolves. The EOS visibility discussion assumes read_committed downstream readers.

7. What exactly changes for source record 11?

ShareCoordinatorService.completeTransaction checks service activity, the target topic and TV2 support, then schedules a regular coordinator write operation. Unlike ordinary output and the group-offset path, this branch does not append a normal end-transaction control record to the share-state log through that handler.

ShareCoordinatorShard.completeTransaction scans its shareStateMap. isMatchingPendingBatch selects only TX_PENDING batches whose staged producer ID matches and whose staged epoch equals markerEpoch-1 for TV2. It can match several source keys belonging to this transaction on the same shard; it leaves other producers and epochs alone.

DecisionfinalDeliveryStateResult for source work
COMMIT + ACCEPTACKNOWLEDGEDCompletion recorded; record 11 is not acquired again for this group.
COMMIT + REJECTStored staged disposition, e.g. ARCHIVING or ARCHIVEDArchiving may still need separate DLQ work. Marker success does not prove a DLQ publication finished.
ABORTAVAILABLEEligible for reacquisition after source-cache refresh; no successful completion recorded.

The shard creates replacement PersisterStateBatch values without staged transaction metadata, increments deliveryCompleteCount only for ACKNOWLEDGED/ARCHIVED, increments snapshotEpoch, and returns new ShareSnapshot records plus affected keys. CoordinatorWriteEvent.run appends/replays them. High-watermark advancement releases deferred writes; only then does the completion future report success.

After success, KafkaApis invalidates affected local SharePartition caches. If the source leader is remote, its next fetch detects cached TX_PENDING and reloads durable state. This is eventual refresh, not a cluster-wide invalidation broadcast. Local invalidation errors do not reverse the durable decision.

Atomic outcome does not promise simultaneous visibility, a global consumer snapshot, or completion of external side effects. Once the durable state is terminal, a duplicate matching marker finds no TX_PENDING batch to change.

9. What this branch does not yet prove

Confirmed code gap: membership validation is local

The source broker's KafkaApis calls its own groupCoordinator.validateShareGroupMember. That method schedules a read for the group's __consumer_offsets shard in its local CoordinatorRuntime. There is no forwarding in this method. A source broker that does not own the group shard cannot complete this validation normally.

The producer handler targets the source partition and retries retriable NOT_COORDINATOR errors; retrying that source leader does not move group ownership. With source partitions on different brokers, they cannot all be co-located with one group's coordinator. This is a source-derived multi-broker staging limitation, not a fault-injection result.

A remote validation/forwarding or another correctly fenced membership-validation design is needed. This note does not implement a fix. Single-broker tests and mocked service tests cannot establish that arbitrary placement works.

Exact local validation method · Producer target and retry · Local runtime ownership check

Review gap: share completion accepts coordinatorEpoch but does not enforce it here

ShareCoordinatorService.completeTransaction accepts coordinatorEpoch but neither checks nor forwards it to the shard. The shard matches staged producer ID/epoch. Ordinary output marker validation explicitly checks the coordinator epoch. This is a real implementation difference; it does not alone prove an exploitable incorrect commit. Stale/conflicting marker and failover scenarios need explicit coverage before claiming equivalent fencing.

Scaling, engine boundaries and missing integration evidence

Share completion scans the shard's shareStateMap and constructs replacement snapshots for matching keys. There is no producer-indexed lookup in this method; cost depends on shard state, not only the number of ACKs in this transaction.

Multiple worker producers normally own different transactions. A common share group does not merge them. One worker can atomically cover several output partitions plus its staged source ACKs; independently committed transactions in different Flink sink subtasks are not made globally atomic by an ACK owner.

A filter can commit acknowledgement-only work. A one-to-many mapping can include all output records and one input ACK in one transaction, provided that one transaction owns the entire fan-out. Cross-cluster output and arbitrary external side effects are outside this boundary.

The group-membership gate, coordinator-epoch difference and remote cache liveness require dedicated multi-broker tests. The tests run below validate components; they do not establish complete distributed EOS for this prototype.
