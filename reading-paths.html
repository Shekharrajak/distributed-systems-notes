How to read the field guide

Start with one question, then follow the code

Choose a runtime, follow one event, and identify the durable fact that survives a crash. You do not need to read every chapter or schema in order.

Choose your question

“Where does my record go, and which broker owns it?”

Start with Kafka’s record journey. Continue to partition leadership, then group and share ownership. Use the RPC atlas only when you need message fields. A partition leader, group coordinator and transaction coordinator may be different brokers.

“Why is produced output not visible, and what does commit mean?”

Read transaction basics, then decision, markers and recovery. For KIP-1289, continue to share transactions across brokers; that page uses a separate development revision with explicitly recorded gaps.

“How does Flink recover source, state and sink together?”

Start with process and task ownership. Then read checkpoint recovery and the Kafka connector. Use planning and chaining to explain placement and records, backpressure and watermarks to explain stalls. The long runtime walkthrough is the detailed reference once those boundaries are familiar.

“Why can Spark replay a batch but duplicate Kafka output?”

Start with the two micro-batch logs. Follow ranges across executors and state and sink recovery. Use scheduling and shuffle for lost intermediate work. Compare offset APIs only after choosing ordinary Structured Streaming or legacy DStreams.

“Should I think in Streams tasks or Connect workers?”

Kafka Streams embeds processing/state tasks in applications. Kafka Connect runs connector source/sink tasks in workers. Start from the actual runtime; a Flink KafkaSource is not a Connect source task.

“When do table rows become visible, and where does native execution run?”

Read Iceberg publication, then DataFusion execution, Comet inside Spark, and local Arrow ownership. Separate durable table metadata from in-process buffers. Finish with one event and its crash windows and design tradeoffs.

Move from a system diagram into a method

  1. Name one unit of work. A Kafka record, a Flink checkpoint, a Spark task attempt and an Iceberg snapshot are different units. Use one event ID to correlate them; do not assume their numeric IDs match.
  2. Locate its owner. Name the process and the key it owns. Then name the thread/queue only if it changes ordering or failure behavior.
  3. Label each boundary. A direct call, queue handoff, RPC and replicated append have different success meanings. “The call returned” is not always “the work is durable.”
  4. Find the durable fact. Identify the log record, completed checkpoint, state version or published metadata that a replacement reads.
  5. Stop at one crash. Ask what was durable before the crash, what may already be visible, and what can safely repeat.
  6. Open the linked methods. Trace caller, validation, state mutation, persistence, callback and replay. An excerpt is an entry point; inspect the full pinned method when reviewing a guarantee.

Terms that are easy to mix up

Process, pod, task, thread
A process holds memory; a pod is a deployment container; a task is scheduled work; a thread executes it. One process can run many tasks and threads. See Flink placement and Spark placement.
Partition and shard
Always name the namespace. A Kafka input partition, an internal coordinator shard, a Flink key group and a Spark state partition are different ownership units. The same number does not imply the same data or broker.
Leader and coordinator
A partition leader serves a particular log. A coordinator manages keys mapped to its backing internal-topic partition. The controller maintains cluster metadata. See the ownership map.
Offset, position and safe frontier
An offset identifies a position within one Kafka partition. Consumer position is its next read position; the safe processing frontier covers work whose required effects are complete. A stored restart offset normally identifies the next work, not the last finished record.
LEO, HW and LSO
Log end offset is the next append position in a replica. High watermark bounds replicated progress. Last stable offset also accounts for unresolved transactions and bounds read_committed visibility. None is an application’s completed-work counter. See the numeric example.
ACK, commit and publication
Always ask what was acknowledged: request acceptance, replicated append, input progress, transaction outcome or visible table metadata. A successful Kafka OffsetCommit is not a database commit. See the offset comparison.
Checkpoint, snapshot and state version
A Flink checkpoint coordinates a recovery cut. A Spark state version belongs to an operator partition and batch lineage. An Iceberg snapshot defines a published table view. These objects have different completion rules; there is no shared global snapshot service.
Epoch, attempt and fencing
An epoch or attempt identifies an ownership generation in a particular protocol. Fencing rejects obsolete work at the enforcing authority. It is different from merely suspecting a process through a timeout. See Kafka’s epoch distinctions.
Replay and deduplication
Replay repeats input/computation after failure. Deduplication prevents a defined duplicate effect. Producer idempotence recognizes applicable protocol retries; it does not make arbitrary repeated business sends unique.
Durability, visibility and processing completion
Data may be stored but not yet visible to transactional readers. Visible output may not yet be processed downstream. State each guarantee separately.
Backpressure and event-time progress
Backpressure reflects capacity to move/process records. A watermark reflects event-time progress under a policy. A fast CPU cannot make an idle or lagging input’s watermark advance without appropriate semantics.
Exactly-once
Name the observable effect and recovery boundary. Code may execute more than once while only one logical result is committed. A sink’s contract and retained input/state are part of that guarantee; the framework name alone is insufficient.

Clarity review: what changed and why

Reviewed the 28 published content pages, their chapter relationships and evidence entry points. The remaining 23 tracked HTML pages are redirect aliases, not additional technical chapters. Local untracked drafts and preview exports were left untouched; they are outside the published site build.

The main issues were abstract ownership terms without an initial example, overloaded progress/commit vocabulary, dense tables without a reading route, and code references separated from the question they answer. The existing detailed material is retained. The additions put a small example before it and connect each step to the relevant evidence.

This is a readability revision at the existing source pins, not a claim that every engine was rebuilt or all combinations were integration-tested. The KIP-1289 page retains its separate test results and implementation limitations. Baseline chapters and the RPC atlas retain their earlier source scope.
