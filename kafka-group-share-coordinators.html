The mental model

Membership answers who may participate. Acquisition answers who temporarily holds a record. Durable share state answers which work is already completed.

Worked example: connect the system view to the code

Worker A holds record 11 while B completes record 12. Recording 12’s ACK does not require declaring 11 complete. If 11 is released, another worker may acquire it; record 12 remains completed in the group’s durable share state.

    The group coordinator owns membership.

  2. Track record acquisition

  3. Persist delivery state

1. Three different questions, three different owners

QuestionOwnerDurable source
Who is a member and which partitions may it read?Group coordinator, including share-group membership.__consumer_offsets group metadata; protocol-specific member/assignment records.
Which share records are temporarily acquired by a consumer?Source partition leader’s SharePartition cache and timers.A live delivery lease is not the same thing as a durable consumer offset.
Which share records/ranges are acknowledged, available or terminal?Share coordinator for the group/topic-ID/partition key.__share_group_state records, snapshots/updates and start-offset state.

The word “share coordinator” does not replace “group coordinator.” A share consumer uses membership RPCs with the group owner and record-delivery RPCs with source leaders; those leaders persist delivery state through the share coordinator. This extra separation enables concurrent record sharing without a single monotonically committed consumer offset representing every delivery.

Do not tell the audience that every coordinator move necessarily triggers a complete stop-the-world rebalance. The source replays persisted group state and reconstructs timers. Subsequent client heartbeats, expired sessions, lost in-flight join/sync work, protocol version and membership changes determine what reconciliation is needed.

Does a committed group offset prove my sink committed?

No. An ordinary OffsetCommit stores progress; it cannot make an external database insert atomic. Kafka consume-transform-produce can enroll offsets in a producer transaction using the transaction APIs. Standard Flink KafkaSource → KafkaSink instead uses a completed Flink checkpoint and recoverable sink transaction; its optional source OffsetCommit is separate bookkeeping. See the checkpoint boundary.

4. Group coordinator failover, down to the runtime

  1. BrokerMetadataPublisher observes the changed leader of an __consumer_offsets partition and calls GroupCoordinatorService.onElection(partition, leaderEpoch).
  2. CoordinatorRuntime.scheduleLoadOperation creates/loads a shard. The coordinator loader replays records, including relevant transaction control records, into state managers. LOADING is not ACTIVE.
  3. On successful load, the runtime registers high-watermark notifications and calls the shard’s loaded hook. GroupMetadataManager reconstructs membership/session and pending reconciliation timers according to group type.
  4. Requests become keyed runtime events. State-changing results produce records; the writer appends them, and deferred responses wait for the required committed boundary. In-memory replay/speculation is not itself replication.
  5. When ownership is lost, unload cancels/releases outstanding work. Epoch checks prevent stale load/completion work from being treated as the current shard. A new owner rebuilds from the log rather than receiving the old JVM heap.

There are several notions of “snapshot”: the runtime’s timeline snapshots support committed reads/rollback, share-state snapshot records summarize state, and KRaft file snapshots compact metadata replay. They are not one global snapshot service.

SharePartition.rollbackOrProcessStateUpdates holds provisional changes while the persister writes state. A failure rolls them back, accounting for concurrent timeout/state changes; success finalizes them. The persister carries source leader epoch and state epoch with each batch. A successful state record belongs in __share_group_state, not the user topic.

The state topic’s configuration in this checkout uses delete policy with coordinator-managed pruning and snapshot/update records. It is incorrect to say “all Kafka internal state topics are compacted in the same way.” Share acquisition memory, state snapshots, and group membership each need their own recovery explanation.

6. Source-leader failure versus share-coordinator failure

Failure windowRecoveryRemaining ambiguity / limit
Consumer crashes after business action, before ACCEPTAcquisition is eventually released/expired; another consumer can receive it.The action may execute twice. Use idempotency keys, deduplication or an explicit transactional integration.
ACCEPT response lostThe state write may have succeeded; inspect/retry using supported client semantics.Do not promise every duplicate ack returns success: current ownership/state can reject it.
Source leader dies with acquired recordsNew source leader initializes SharePartition from persisted state, using its newer source leader epoch.Volatile member locks/timers are not transferred as a live JVM object. Unfinished delivery can repeat.
Old source leader sends a delayed state writeShare coordinator compares source leader epoch with its recorded highest epoch.Fencing becomes effective once newer authority is recorded/observed; it is not instantaneous global knowledge.
Share coordinator diesThe __share_group_state shard changes leader and is replayed by the replacement coordinator. Persister rediscovers/retries.State persistence is unavailable while ownership/loading/replication are unresolved, even if source records are readable.
Group coordinator diesReload __consumer_offsets membership and assignment state; clients retry membership operations.This does not itself delete durable share acknowledgement state or elect every source leader.
State write failsProvisional acknowledgement transitions roll back or follow the exception path.A lock may expire concurrently. “Retry any ack forever” is not a safe universal rule.
Share state reinitialized/resetState epoch prevents an earlier incarnation’s writes from overwriting newer state.Operational reset changes processing semantics; it is not transparent repair.
Retention/compaction removed a source recordDelivery code handles gaps/start-offset movement under its rules.A delivery-state log cannot reproduce deleted payload bytes.
Source and state leaders fail togetherBoth partition leadership/replay paths must recover; they can complete in either order.Availability depends on surviving replicas of both logs plus metadata quorum progress.

A subtle but important path is readStateAndMaybeUpdateLeaderEpoch: a new source leader’s read can itself generate a state record to advance the fencing epoch. The read is therefore not always just a cache lookup. Tests explicitly reject lower source leader epochs and lower state epochs without generating write records.

7. Ordinary share ACK is not transactional share EOS

Scope boundary: the pinned Kafka snapshot used by this guide has no TxnShareAcknowledgeRequest.json and no TX_PENDING state. This chapter describes its ordinary share-delivery path. The separate KIP-1289 development design must not be silently drawn into these diagrams.

The architectural problem is easy to see: output committed but input ACCEPT lost can duplicate processing; input ACCEPT committed but output failed can lose the intended result. Ordinary acknowledgement RPCs alone do not atomically join the two. A transactional-share implementation needs explicit enrollment/staging, durable participant state, fencing and commit/abort completion. Such an implementation must be verified against its own branch and feature gates before claiming end-to-end EOS.

Likewise, the normal Flink KafkaSource is not a share consumer. Do not generalize its checkpointed next-offset model into share record-ack state. This guide keeps the two protocols separate.

Source: share-states marker-handler

8. Presentation mental model

Group coordinator = membership desk
Source leader     = record delivery desk + temporary locks
Share coordinator = durable delivery ledger

Failure question:
Did we lose a member, a delivery desk, or the ledger owner?
Which log survives, which epoch fences the old owner,
and which request must be retried after the new owner loads?
